- (constraint) [INHERITED AD-3] Centralized proxy pool: auth-required platforms (Facebook) use sticky IP per account, auto-quarantine 429/403 for 5m, no direct connection fallback.
- (constraint) [INHERITED AD-5] Sticky IP per account for Facebook; AbstractLogin returns {accountId, cookies, tokens, expiresAt}; SessionManager owns state.
- (constraint) [INHERITED AD-9] PlatformResponseValidator for Facebook must detect bot challenge/rate-limit even when HTTP 200; auth platforms hibernate account 15-30m and rotate, not proxy hop repeatedly.
- (constraint) [INHERITED AD-13] Adaptive governor throttles by healthyProxyCount, accountVelocity, redisConsumerLag; account rotation when velocity exceeded; all requests through ProxyIpPool.
- (constraint) [INHERITED AD-14] Standard error envelope {code,type,message,retryAfter,suggestedAction,accountId?,platform} for all Facebook operations; governor status API/CLI.
- (constraint) [INHERITED AD-20] Dual-Pool Resource Isolation: realtime (MCP on-demand) 30% capacity, bulk 70%; consumer quota per Nowing/ChainLens.
- (decision) AD-FB-1 [Binds: api/routes/facebook.js, api/services/facebookScrape.js, api/services/facebookAutomation.js, src/scrapers/facebook/**; Prevents: every route/service inventing its own browser launch, login, proxy, and retry logic] Rule: All Facebook scrape and automate operations MUST enter through a single FacebookExecutionGateway. Routes/services are not allowed to call createBrowser, createPage, loginWithCookie, or warmSession directly.
- (decision) AD-FB-2 [Binds: FacebookExecutionGateway, src/core/account-pool.js; Prevents: forcing multi-account pool on single-account operations and losing the simple single-account path] Rule: Gateway supports two modes: (a) SINGLE mode — one account, one browser, one task, for profile/posts/automate; (b) POOL mode — fan-out via AccountPool when caller passes accountIds[] or parallel=true for search-all.
- (decision) AD-FB-3 [Binds: FacebookExecutionGateway, api/services/facebookHealth.js, prisma.facebookAccountHealth; Prevents: launching browsers with dead or checkpointed accounts and wasting proxy/concurrency budget] Rule: Before any browser launch the gateway checks the account health cache. Only status='active' accounts proceed; 'checkpoint', 'hibernating', or 'unknown' accounts are rejected with FB_INVALID_COOKIE or FB_CHECKPOINT error envelope and trigger admin notification if no active account remains.
- (decision) AD-FB-4 [Binds: src/scrapers/facebook/index.js, src/scrapers/facebook/core.js, src/scrapers/facebook/auth.js, src/scrapers/facebook/warmup.js; Prevents: inconsistent anti-bot settings and duplicate browser/session code across routes] Rule: SessionFactory is the only owner of createBrowser, createPage, loginWithCookie, warmSession. It applies fingerprint, viewport, proxy, persistent userDataDir, and anti-detection flags. Gateway delegates to SessionFactory; no other module may launch a browser for Facebook.
- (decision) AD-FB-5 [Binds: prisma.facebookAccount, prisma.facebookAccountHealth, src/core/account-pool.js; Prevents: ambiguous account state and silent reuse of banned accounts] Rule: Facebook account lifecycle states are: active, hibernating (rate-limit/bot-challenge cooldown), quarantined (checkpoint/manual), dead (permanent/cannot relogin). Only AccountPool + Governor may transition state. State changes are persisted to facebookAccountHealth and emit events.
- (decision) AD-FB-6 [Binds: FacebookExecutionGateway, src/core/adaptive-governor.js; Prevents: smashing rate limits and burning accounts because the gateway bypasses the global governor] Rule: Every Facebook operation calls globalAdaptiveRateGovernor.canAccountRequest(accountId, 'facebook') before execution and recordRequest after. If the account is hibernating or over safeRequestsPerMinute, the gateway either waits, rotates in POOL mode, or returns a rate_limit error envelope.
- (decision) AD-FB-7 [Binds: FacebookExecutionGateway, api/services/facebookAutomation.js; Prevents: write actions using the same concurrency/rotation profile as read actions and causing mass account bans] Rule: READ operations (scrape/search) may use POOL mode with concurrency and account rotation. WRITE operations (like/comment/post/share/friend) are SINGLE mode with a human-like delay floor, dry-run gate by default, and no account rotation mid-task.
- (decision) AD-FB-8 [Binds: FacebookExecutionGateway, src/core/error-envelope.js, api/routes/facebook.js; Prevents: routes/services returning inconsistent error shapes and losing retry/rotation signals] Rule: All Facebook errors are wrapped in the standard error envelope {code,type,message,retryAfter,suggestedAction,accountId?,platform} (per parent AD-14). Codes use FB_* prefix. Suggested actions are one of: retry_after_delay, rotate_proxy, rotate_account, hibernate_account, relogin, wait, reduce_rate.
- (decision) AD-FB-9 [Binds: FacebookExecutionGateway, dashboard/**, api/routes/admin/**; Prevents: operators discovering dead accounts only when a scrape fails] Rule: When an account transitions to dead, checkpoint, or all accounts for a user/platform are hibernating, the gateway emits an event (Socket.io / webhook / admin alert). Admin dashboard shows account status, hibernation countdown, and suggested action.
- (decision) AD-FB-10 [Binds: api/services/facebookAccountPool.js, src/core/account-pool.js, api/services/facebookScrape.js; Prevents: big-bang rewrite breaking existing Facebook routes and tests] Rule: Migration is incremental. Phase 1: build gateway alongside existing FacebookAccountPool; routes opt-in for new actions. Phase 2: redirect runSearchAllParallel to gateway POOL mode. Phase 3: deprecate FacebookAccountPool after all existing actions use gateway and tests pass.
- (decision) AD-FB-11 [Binds: FacebookExecutionGateway, src/proxy/proxy-pool.js; Prevents: sticky-IP violations and IP leaks] Rule: The gateway resolves a sticky proxy per account before session creation and passes it to SessionFactory. Auth-required platforms (Facebook) keep the same IP for the entire account session per parent AD-3/AD-5. Proxy change only on proxy failure/quarantine, never per request.
- (decision) AD-FB-12 [Binds: FacebookExecutionGateway, src/scrapers/facebook/index.js; Prevents: platform-specific scrapers being called without a managed session] Rule: Facebook scraper entry points (scrapeProfile, scrapePosts, search, etc.) receive a prepared Page and AccountContext from the gateway and never launch their own browser. They may receive page.evaluate/page.goto but cannot call createBrowser.
- (assumption) [ASSUMPTION] Existing src/core/adaptive-governor.js, src/core/account-pool.js, src/core/error-envelope.js, src/proxy/proxy-pool.js, and src/scrapers/facebook/index.js are reusable with minimal extension rather than rewrite.
- (assumption) [ASSUMPTION] Facebook operations can be classified into READ (profile, posts, search, comments, group) and WRITE (like, comment, post, share, friend, join) risk profiles for the purpose of gateway routing.
- (version) Node.js >= 18 ESM, Puppeteer + puppeteer-extra-plugin-stealth, Prisma 5.x, PostgreSQL, Redis, Express 4.x. No new runtime dependencies required for this spine.
- (question) [OPEN] Should FacebookExecutionGateway be a stateful class managing in-flight sessions, or a stateless function that creates/disposes a browser per operation?
- (question) [OPEN] Should health pre-check be synchronous (blocks until verified) or cache-based with TTL and background re-verification?
- (question) [OPEN] How does the gateway integrate with existing Operation records and Socket.io / webhook emitters without duplicating emit logic from api/routes/facebook.js?
- (direction) [DEFERRED] Concrete method signatures, TypeScript types, and event schemas for the gateway are deferred to the implementation story and bmad-spec companion.
- (direction) [DEFERRED] Dashboard admin UI for account status, hibernation, and alerts is deferred to parent AD-19; this spine only defines the gateway event contract.
